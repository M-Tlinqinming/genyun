## 1. 第一期范围（方案 B）

**原则**：主线全部线上化，收款和开票先人工处理。外部审核（备案、商户号）不卡开发进度。

### 1.1 线上完成

- 企业两种开始方式都做：**按提示填写（4 步）**、**上传已有资料**，之后进入同一条审核与交付流程。
- AI 起草 → 注册安全工程师整理、编制、Word 校对、补件、客服电话核实 → 发布。
- 告知费用 → 客户确认费用 → 对公转账 → 运营确认到账 → 客户下载三份 Word。
- 运营端：开通组织与邀请首位管理员、分配专业人员、待联系客户、知识库、反馈受理、收款确认、待开票。
- 官网（独立静态站）。

### 1.2 第一期人工处理

| 环节 | 第一期 | 以后 |
|---|---|---|
| 收款 | 对公转账，运营后台手工确认到账 | 微信支付 / 支付宝 |
| 定价 | 运营每单人工填写金额（系统记录每单价格） | 价格稳定后做价目表，自动计算 |
| 发票 | 财务在电子发票服务平台手工开数电票，上传到系统 | 接口自动开票 |
| 安全服务机构年度服务 | 线下签合同，运营开通组织时填写到期日 | 线上续费 |

## 2. 从设计到代码

- **不用 Ant Design Pro 等后台模板**，在 Ant Design 6 上自建框架，通用功能用成熟开源库。
  - 原因：ProComponents 正式版（2.8.10）只支持 antd 5，支持 antd 6 的 3.x 还是 beta（3.1.15-7）；模板的默认布局和外观与设计不符，改造成本高于自建。（2026-10-23 查 npm）
  - 原则：耕云独有的业务逻辑（订单状态、权限、补件流程）自己写；页面跳转、数据加载、表单校验等通用功能用成熟库。
- **开发顺序**：
  1. 设计 token → Ant Design 主题配置；
  2. 通用组件（顶栏 64 / 侧栏 224 框架、状态标签、来源标签、分步向导、右侧说明栏、上传区）；
  3. 逐页开发。
- **每页的做法**：通过 Paper MCP（`get_jsx` / `get_computed_styles` / token）取精确值，不从截图估算；开发后截图，与 Paper 并排比对并修正。
- **设计依据**：Paper 10–16 页高保真；20–22 线框只补高保真未覆盖的部分；90–97 归档不用。
- **颜色 token**：只用 `gy-v1-*`（产品后台）和 `gy-brand-*`（官网）。旧的绿色 token（`--color-primary` #2D7A52 等）**废弃**。
- **没有高保真的新页面**（确认费用、待付款、收款确认、开票信息、待开票、发票下载）：按现有设计系统直接开发，开发后验收，不再补高保真。

## 3. 技术架构

| 部分 | 选型 | 理由 |
|---|---|---|
| 后台前端 | React + TypeScript + Ant Design 6，三端（客户 / 专家 / 运营）放在一个单页应用里，登录后按身份进入不同工作区 | 设计基于 antd 6；三端共用主题和组件 |
| 官网 | 独立静态站 | 视觉与后台不同；需要被搜索引擎收录、打开快；备案时要有可访问的官网 |
| 后端 | Node.js + TypeScript，NestJS | 复用旧仓库资产；前后端共用一套字段规则；权限检查有统一位置 |
| 耗时任务 | Redis + 任务队列（AI 起草、Word 生成在后台执行，页面显示进度，完成后站内 + 邮件通知） | 避免请求超时 |
| 数据库 | PostgreSQL（阿里云托管版） | 旧仓库同库，表结构可参考；备份和高可用由云厂商负责 |
| 文件 | 阿里云对象存储，私有读写，服务器端加密；下载用短时效签名链接 | 文件没有公开地址 |
| Word 生成 | 沿用旧仓库流程：Markdown 模板 → Pandoc + Word 样式模板 → 后处理；流程图用 mermaid 渲染 | Martin 确认旧格式可接受 |
| 部署 | Docker 镜像（含 Pandoc、mermaid 渲染工具） | 不绑定云厂商，可直接迁移 |

### 3.1 从旧仓库复用 / 替换

旧仓库：`D:\001-Project\_ref\emergency-plan-templates`

- **复用**：字段与校验规则（zod）、判断需要哪些预案的决策引擎、模板（综合预案、专项预案、现场处置方案）、Word 生成流程、飞宇样例数据（作为测试样本）。
- **不复用**：界面（Tailwind / Radix，改用 antd 6）；旧的「客户自填全部专业内容」流程（按新设计重做）。
- **必须替换**：Supabase（登录、存储）和 Vercel（部署）都是境外服务，换成自建登录 + 阿里云。

### 3.2 账户与权限

| 身份 | 数据范围 |
|---|---|
| 客户组织管理员 | 本组织全部数据；邀请成员 |
| 客户组织成员 | 本组织数据（按设计的权限） |
| 专业人员 | 只能看分配给自己的任务 |
| 运营管理员（兼客服） | 全部组织；开通、分配、客服联系、确认收款、开票 |

- 权限判断全部在后端，前端隐藏按钮只是展示效果。
- 每次读写都校验「所属组织 + 角色 + 任务分配」。
- 越权自动测试（例：A 组织账号读取 B 组织文件必须失败）每次提交都运行。
- 密码用成熟算法加密存储；邮箱验证码重设密码；不接短信。

### 3.3 待开发时验证的技术点

- 专家端「Word 校对」页的浏览器预览方式：后台转 PDF，或前端直接渲染 .docx。开发到这一页时先做小样给 Martin 看效果，再定。

## 4. 合规与部署

### 4.1 已定

- **云厂商**：阿里云（已购买），华南机房（深圳或广州）。
- **域名**：`genyun.net.cn`（已购买）。正式环境用 `genyun.net.cn`，预览环境用 `staging.genyun.net.cn`，发信用子域名（如 `mail.genyun.net.cn`）。
- **大模型**：只用已在网信办备案的国产大模型，通过阿里云百炼调用；上线前在网信办公布的已备案清单里核对模型名称和备案号。选择承诺不用客户数据训练的服务；发送前去掉不必要的个人信息。
- **AI 的定位**：AI 只做专家的内部起草工具，客户看不到未经审核的 AI 稿。系统记录每份文件使用的模型和审核的注安师。
- **AI 标识**：交付的 Word **正文不加**可见的 AI 说明，只在文件元数据中写入「AI 辅助起草、注册安全工程师审核」。如网信办答复要求可见标识，再调整。
- **安全建设**：按等保二级要求建设，包括加密存储、全程 HTTPS、操作日志、定期备份、最小权限。正式定级备案和测评安排在上线后。
- **邮件**：阿里云邮件推送，用子域名发信，配置 SPF、DKIM、DMARC。免费额度为每账号 2000 封、每天最多免费 200 封，初始每日上限 2000 封。

### 4.2 网站备案（尽快启动，与开发并行）

1. **ICP 备案**：域名持有人须与备案主体（惠州元御智能科技有限公司）一致并完成实名认证；需要阿里云中国内地服务器。阿里云初审约 1–2 个工作日，广东省通信管理局审核一般 1–20 个工作日，不能加急。
2. **公安联网备案**：网站开通后 30 日内，在全国互联网安全管理服务平台提交。

### 4.3 ⚠️ 待核实事项（Martin 负责）

## 5. 收款与发票

### 5.1 订单状态

```
已提交（不收费）
  → 审核中
  → 待确认费用（运营填写金额）
      └─ 客户不接受 → 已关闭
  → 待付款（客户确认费用，系统记录确认人和时间）
  → 已付款（运营核对订单号、金额、付款单位后确认）
  → 可下载
  → 修订期（交付后 3 天内，因事实变化可免费修订 2 次）
```

- 待付款页显示对公账户、金额，以及「转账备注请填：订单号」。
- 运营确认到账的承诺时间：**一个工作日内**。超时未确认的订单在运营后台标红。
- 「付款方式」是订单上的独立字段，第一期只有「对公转账」，以后加微信或支付宝不改流程。
- 年度服务组织在合同有效期内提交的任务，跳过付款环节。
- 客户确认了费用但未付款：第一期只在运营后台列出，由客服跟进，不自动关闭。

### 5.2 发票

- 依据国家税务总局公告 2024 年第 11 号：数电发票自 2024 年 12 月 1 日起全国推广，增值税专用发票也包括在内，与纸质发票具有同等法律效力，通过电子发票服务平台免费开具。
- 流程：客户在组织设置中填写开票信息（抬头、税号；专票加地址电话、开户行账号）→ 付款确认后进入「待开票」→ 财务在电子发票服务平台开票 → 上传到系统 → 客户在订单里下载，同时收到邮件通知。

### 5.3 以后接在线支付的前提

- **微信支付（电脑网页扫码）**：企业可申请；需要已认证的服务号（或已认证的小程序、App）绑定商户号。建议提前注册并认证公司服务号。
- **支付宝（电脑网站支付）**：第三方资料显示要求网站已完成企业 ICP 备案。⚠️ 未能核实支付宝官方文档。
- 两家手续费以商户后台为准。⚠️ 未查到官方费率。

## 6. 工作方式

### 6.1 代码管理

- 代码托管在 GitHub 私有仓库。`main` = 正式线上版本；每块功能在独立分支开发，通过检查后再合并。
- **铁律**：真实客户数据和密钥（数据库、大模型、邮件等）绝不进仓库，统一存放在服务器配置中。

### 6.2 三道质量关

1. **自动测试**（不通过不能合并）：业务规则（字段校验、决策引擎、订单状态）；越权测试；主线全流程浏览器测试（提交 → 审核 → 确认费用 → 确认到账 → 下载）。
2. **代码审查**：每个分支合并前做独立审查；**上线前请外部资深工程师做一次安全审查**（Martin 已同意安排预算），见 6.5。
3. **Martin 验收**：预览链接 + 设计稿与实际页面的并排截图 + 用业务语言写的检查清单。

### 6.3 环境

| 时期 | 预览环境 | 正式环境 |
|---|---|---|
| ICP 备案完成前 | 阿里云香港小服务器，只用虚构样例数据 | 无 |
| ICP 备案完成后 | `staging.genyun.net.cn`（境内，独立数据库） | `genyun.net.cn` |

### 6.4 里程碑

| 里程碑 | 内容 | 验收物 |
|---|---|---|
| M0 地基 | 主题、通用组件、登录、三端框架、自动部署 | 能登录，看到三个工作区框架 |
| M1 客户提交 | 建档、两种开始方式、检查与提交 | 用样例企业从头填到提交 |
| M2 专家处理 | 任务中心、整理、AI 起草、编制、Word 校对、补件、客服核实、发布 | 第一份系统生成的三件套 Word |
| M3 收款与运营 | 确认费用、到账确认、开票、组织开通与邀请、知识库、反馈 | 一单从提交走到付款、下载、拿到发票 |
| M4 官网与上线 | 官网、发信配置、外部安全审查、正式环境、监控与备份 | 正式上线 |

- M2 排在 M3 前：AI 起草和 Word 生成技术风险最大，要尽早暴露问题。
- ICP 备案和 4.3 的政策咨询与 M0 同时启动，最晚在 M3 结束前要有结果。

### 6.5 外部安全审查范围（供询价）

- 登录、会话、密码重设、邀请链接（含过期处理）；
- 多组织数据隔离与角色权限（客户组织 / 专业人员 / 运营管理员），越权访问测试；
- 文件上传与下载（类型校验、私有存储、签名链接时效）；
- 订单与收款状态能否被绕过（未付款下载）；
- 密钥管理、日志与备份；
- 交付形式：问题清单 + 风险等级 + 复测。
